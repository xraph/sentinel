Sentinel is a set of focused Go packages. The `engine` package is the coordinator. The rest define entities, interfaces and the pieces that plug into it.

## Package diagram

## Engine construction

`engine.New` takes option functions and returns `(*Engine, error)`:

```go
cfg := sentinel.DefaultConfig()
cfg.DefaultModel = "gpt-4o"
cfg.PassThreshold = 0.8
cfg.Concurrency = 8

eng, err := engine.New(
    engine.WithStore(st),
    engine.WithConfig(cfg),
    engine.WithExtension(observability.NewMetricsExtension()),
)
```

`engine.WithLogger` takes a go-utils `log.Logger`; without it the engine logs nothing. `engine.WithMetrics` takes a go-utils `metrics.Metrics`; without it the engine records no metrics. Spans need no option, see [Observability](/docs/infrastructure/observability). `engine.WithTarget` and `engine.WithScorer` register targets and scorers by name, for runs started by name and for the dashboard. See [Configuration](/docs/concepts/configuration).

## Evaluation flow

`RunEval` (synchronous, with target and scorer values) and `StartRun` (asynchronous, with registered names) share one pipeline:

1. Load the suite and its cases. A suite with no cases is refused with `ErrEmptyInput` before anything is written. The prompt is the suite's current prompt version if it has one, else the suite's `SystemPrompt`. The model is the run's, else the suite's. The temperature is the suite's, else the configured default.

2. Create the run in state `running`, recording the threshold, concurrency, target, scorers, model and prompt version in its `Config`. `OnEvalRunStarted` fires, and `OnPersonaEvalStarted` too when the run or suite has a `PersonaRef`.

3. Call the target with each case's input, at most `Concurrency` cases at once. The prompt, model and temperature reach the target through the context (`target.CallOptionsFrom`). Before scheduling each case the runner checks whether the run was cancelled, so a `CancelRun` from another replica stops it.

4. Score the output with the run's scorers, then the case's own scorers resolved by name from the registry. The case's score is the average. It passes at `PassThreshold` or above. A target error, a scorer error or an unknown scorer name makes it `error`. Each result is stored as soon as the case finishes.

5. Read the counters back from the store and finalise the run as `completed`, or `failed` when results couldn't be stored or the stats couldn't be read. A cancelled run stays `cancelled`.

6. For a completed run, compare it with the suite's current baseline. If anything fell by more than `RegressionThreshold`, `OnRegressionDetected` fires. No baseline means no comparison.

## App scoping

`sentinel.WithApp(ctx, id)` puts an app ID on the context. `CreateSuite` stamps it on a suite that has no `AppID`, and runs take the suite's. List filters (`suite.ListFilter`, `evalrun.ListFilter`) take an app ID, and an empty one matches every app. Lookups by ID aren't scoped. `sentinel.WithTenant` stores a tenant ID that nothing in Sentinel reads yet. See [Multi-Tenancy](/docs/concepts/multi-tenancy).

## Plugin system

Plugins implement `plugin.Extension` (just `Name() string`) and opt in to hooks by implementing more interfaces:

```go
type Extension interface {
    Name() string
}

// Opt-in hooks (implement any subset):
type EvalRunStarted interface {
    OnEvalRunStarted(ctx context.Context, suiteID id.SuiteID, runID id.EvalRunID, model string) error
}
type EvalRunCompleted interface { /* ... */ }
type CaseCompleted interface { /* ... */ }
type RegressionDetected interface { /* ... */ }
// ... 15 hook interfaces in all
```

The `plugin.Registry` sorts plugins by hook when you register them, so an event only calls the plugins that implement it. Hook errors are logged and never stop the pipeline. See [Plugins](/docs/infrastructure/plugins).

Built-in plugins:
- `observability.MetricsExtension`: unlabelled counters for lifecycle events, older than the engine's own metrics
- `audithook.Extension`: turns lifecycle events into audit records
